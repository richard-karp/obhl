## The model, in one table

Three tiers, one rule. **You may write a profile only if your tier is strictly
above theirs.**

| Tier | Reach | May write |
|---|---|---|
| Commissioner | every league, present and future | anyone except another commissioner |
| Deputy | every league, present and future | anyone outside the office |
| League manager | leagues they are a member of | tier-0 accounts whose leagues theirs contain, never another manager |

Consequences that are easy to misread, so they are stated: a **deputy cannot
touch the office at all**; the **commissioner tier is not editable from the app
by anyone** (peer-flat, so no commissioner outranks another — appointment is
SQL). Containment survives untouched at tier 0.

## Phase 1 — `supabase/migrations/0034_league_office.sql`

```sql
create type office_tier as enum ('deputy', 'commissioner');

create table league_office (
  profile_id uuid primary key references profiles(id) on delete cascade,
  tier       office_tier not null,
  created_at timestamptz not null default now()
);
alter table league_office enable row level security;
```

**No grants to `authenticated`, and no policies — deliberately.** 0009's
blanket `grant insert, update, delete on all tables in schema public` ran long
before this table existed, so a new table starts with none (0032 hit the same
thing and granted explicitly; this one does not). This departs from the
codebase's usual "app guard plus an independent RLS half", and **the reason
belongs in the migration header**: an absent grant is stronger than any policy.
A policy can be written wrong or dropped by a later migration meaning to replace
it; a table `authenticated` cannot write at all has no such failure mode. Every
legitimate write is the admin client, on the service role. `select` is not
granted either — the helpers are `security definer`, and every page that lists
the office reads on the admin client.

Two helpers, both `security definer set search_path = public` (0032's convention):

```sql
create or replace function public.office_tier_of(p_profile uuid)
returns office_tier language sql stable security definer set search_path = public as $$
  select tier from league_office where profile_id = p_profile;
$$;

create or replace function public.my_office_tier()
returns office_tier language sql stable security definer set search_path = public as $$
  select tier from league_office where profile_id = auth.uid();
$$;
```

### Trap A — `is_league_member(null)` must stay false ⚠️ a reading

"Full manager of every league" is delivered by one branch:

```sql
create or replace function public.is_league_member(p_league uuid)
returns boolean language sql stable security definer set search_path = public as $$
  select p_league is not null and (
    public.my_office_tier() is not null
    or exists (
      select 1 from profile_leagues
      where profile_id = auth.uid() and league_id = p_league
    )
  );
$$;
```

`manages_league(l)` is already `auth_role() = 'league_manager' and
is_league_member(l)`, so an office member whose `profiles.role` stays
`league_manager` gains all ~20 role-keyed policies in 0009/0032 **with no edit
to any of them**. That is why this design is small.

⛔ **`p_league is not null` is load-bearing and new.** The existing body fails
closed only *incidentally*, because `league_id = null` is never true. An `or`
branch that does not mention `p_league` destroys that. Without the explicit
guard a commissioner passes `manages_league(null)` — and null is what
`logo_object_league` returns for a malformed storage path, what `season_league`
returns for a deleted season, and what every pre-0031 audit row carries. The
office would silently gain write access to every unresolvable and orphaned
object in the instance.

### Trap B — `contains_leagues_of` passes *vacuously* for the office ⚠️ a reading

An office member has **no `profile_leagues` rows** — membership here is a rule,
not data. `contains_leagues_of` asks "is there a league of theirs that is not
mine", so over an empty set it returns true for *any* caller. Reachable: an
ordinary league manager satisfies `auth_role() = 'league_manager'`, so as
written today they would pass `manager write profiles` against a commissioner
and rewrite their `profiles.role`. The precedence function must refuse the
office **explicitly** rather than lean on containment:

```sql
create or replace function public.may_write_profile(p_profile uuid)
returns boolean language sql stable security definer set search_path = public as $$
  select case public.my_office_tier()
    when 'commissioner' then public.office_tier_of(p_profile) is distinct from 'commissioner'
    when 'deputy'       then public.office_tier_of(p_profile) is null
    else public.office_tier_of(p_profile) is null
         and public.contains_leagues_of(p_profile)
  end;
$$;
```

`is distinct from` rather than `<>` **on purpose**: `office_tier_of` returns
null for everyone outside the office, and `null <> 'commissioner'` is null, not
true — which would refuse a commissioner every ordinary write.

`contains_leagues_of` (0033) is unchanged and now has exactly one caller. The
policy swaps which function it names:

```sql
drop policy "manager write profiles" on profiles;
create policy "manager write profiles" on profiles
  for all to authenticated
  using (public.auth_role() = 'league_manager' and public.may_write_profile(id))
  with check (public.auth_role() = 'league_manager' and public.may_write_profile(id));
```

`manager read profiles` keeps `shares_league_with`, as 0033 left it. Note what
that now means: **an office member shares a league with everyone, so they read
every profile in the instance.** Intended, recorded here so it is not later
discovered and mistaken for a leak.

**Probe A** — as a commissioner on the **anon key**, attempt a write gated on a

⚠️ **Read the row back.** An RLS-refused `UPDATE` reports **no error** and
matches zero rows — the exact failure mode `ACCESS_CONTROL_HANDOFF.md`'s

⛔ **Falsify before believing.** For each probe: knock its guard out (drop the

and watch it go green. A probe never seen failing is not evidence that the guard
works — it may be testing nothing. Record both transitions in this file.

Use the anon key, not the service role: the service role bypasses RLS and every
probe passes vacuously.

### The role invariant, enforced in SQL — watched 2026-09-03

Code review found that the office multiplies REACH, not ROLE (open question 2),
and that **nothing enforced the `league_manager` precondition it assumes**. Two
triggers in 0034 now do, both watched with `scratchpad/probe-triggers.mjs` on the
**service role** — deliberately, because the admin client and hand-written SQL are
the only writers, and hand-written SQL is the sole way to make a commissioner:

| | result |
|---|---|
| appointing a scorekeeper | **rejected** ✓ |
| control: appointing a manager | accepted ✓ |
| demoting a sitting commissioner | **rejected** ✓ |
| role unchanged on read-back | ✓ |
| control: remove the tier, then change the role | works ✓ |

The second trigger is not a new rule — it enforces the two-step revocation §6 of
the design already documents (remove the tier, *then* the role is changeable).
That ordering was previously a convention the UI observed and the server did not:
`may_write_profile` lets a commissioner write a deputy, so demoting one and
leaving the tier attached was reachable.

## Phase 4a — People & Roles (`/[league]/manage/people`)

Unions office members into the league's staff list, labelled **Commissioner**
and **Deputy**. The page's `members` query reads `profile_leagues` for the
league, which office members are **not in**, so this is an explicit union, not
something that happens by itself.

Office rows are **read-only there for everyone, including commissioners.** The
tier is managed in exactly one place (Phase 4b). A row offering to change a
deputy's underlying role while their tier lives on another page invites the
wrong mental model of what the row controls.

⚠️ This makes the **surface narrower than the permission**: the model lets a
commissioner write a deputy, and no control here offers it. Deliberate. The path
is two steps, each in one place — remove the tier in League Office, at which
point the person is an ordinary manager row here and their role is changeable.

`canChangeRole` becomes the precedence test, so what renders and what the server
permits keep agreeing — the property `staff-row-actions.tsx` already documents,
and the reason it renders a *reason* instead of a control that does nothing.

**Labels, fixed once so they do not drift:** the role column and the League
Office roster read **Commissioner** and **Deputy**; audit prose reads "a
commissioner" and "a deputy commissioner".

## Phase 6 — bootstrapping

The tier is peer-flat, so the **first commissioner cannot be created from the
app**. Two paths: `scripts/seed-users.mjs` appoints one for local and e2e; a
documented SQL snippet in `LAUNCH_READINESS_HANDOFF.md` for production.

Appointing someone **does not touch their `profile_leagues` rows**, and nothing
here deletes them. A manager promoted to deputy keeps the rows they had; they go
inert while the office branch of `memberLeagueIds` answers first. Removing the
tier therefore restores exactly the reach the person had before, with no repair
step — **the tier is purely additive**, which is what makes revocation clean.

⛔ **The seed must add new accounts, never elevate an existing fixture.**
`seed-users.mjs` has five, and its header explains why the last two exist:
without them the suite runs as a manager who belongs to everything and every
cross-league guard passes whether or not it holds. `16-league-membership.spec.ts`

only) and asserts the role control is **absent**. Elevating `manager@obhl.test`
would give every Manager test office powers and the cross-league guards would
stop being exercised **while still reporting green**. Add a **sixth and seventh**
account — commissioner and deputy — and leave all five existing fixtures alone.

## Open questions — the spec does not settle these

**1. RESOLVED 2026-09-03 — a commissioner may take a league to zero managers.**
Decided by the user; built in Phase 3. No last-manager check is added.

The reasoning, recorded because the code comment is short: the office reaches
every league present and future, so whoever emptied a league can also appoint the
replacement. It is not a one-way door, and refusing would rebuild the exact dead
end the office exists to remove — a league in a state only SQL can fix. The
asymmetry that keeps it safe is that a MANAGER still cannot do it: the
self-removal rule is untouched for them, so the only tier that can empty a league
is the tier that can repair it.

**2. The office multiplies REACH, not ROLE — and nothing enforces the role it
assumes.** ⚠️ A reading, confirmed against both halves of the code.

Both gates test `profiles.role` *before* membership is ever consulted:

- RLS: `manages_league(l)` is `auth_role() = 'league_manager' and is_league_member(l)`
  (`0032:54`). The office branch lives inside `is_league_member`, so it widens
  *which leagues* count — it does not make anyone a manager.
- App: `requireLeagueRole` (`src/lib/auth/guards.ts:61`) calls `requireRole`
  first, which redirects on a role mismatch before `isLeagueMember` runs. The
  office branch in `memberLeagueIds` never gets a chance.

So the design has an unstated precondition: **every office member must hold
`profiles.role = 'league_manager'`.** The spec assumes it in passing ("an office
member whose `profiles.role` stays `league_manager`") and nothing checks it.
Appoint a `captain` and you get a commissioner with **no manager powers at all**;
appoint a `scorekeeper` and you get scorekeeping in *every* league
(`keeps_score_for` is gated the same way) and still no manager powers.

**A commissioner who also plays is fine, and needs no new model.** The captain
surface was already moved off role-gating and onto the player link — see
`src/app/[league]/manage/dashboard/page.tsx:112` ("A person can be a manager
*and* captain a team — manager write access is a superset of a captain's") and
`.../manage/score/[gameId]/page.tsx:93`. `is_captain_of` (`0009:16`) derives from
`team_players.is_captain` joined through `profiles.player_id`, never from
`profiles.role`. So a playing commissioner is `role = 'league_manager'` **with a
`player_id`**, and their captaincy still works. Captain powers do NOT leak across
leagues via the office, because `is_captain_of` does not call `is_league_member`.

Consequences to build:

- **Phase 4b** must refuse to appoint anyone whose `profiles.role` is not
  `league_manager` (or promote them as part of the appointment, and log it).
  A silently powerless commissioner is the worst outcome here.
- **Phase 6** must give the seeded commissioner a `player_id`, so the
  commissioner-who-plays case is actually exercised rather than assumed.
- **Phase 7** should add the two negative cells: a captain-tiered and a
  scorekeeper-tiered office member get no manager write.

**3. Whether Phase 4b's appoint control needs its own containment story.**
Appointing a deputy is a write to `league_office`, not to `profiles`, so
`may_write_profile` does not gate it. The spec asserts the page is "visible to
the office only" and that only commissioners see controls, but never names the
